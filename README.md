## Quickstart

### Секреты

Проект хранит секреты в специальном файле: `.env.secrets`
Для быстрого старта копируем:

```bash
cp .env.secrets.example .env.secrets
```
(Далее меняем его при необходимости).

Переменные в `.env.secrets`:

- `APP_PORT` — HTTP порт (дефолт `8080`)
- `LOG_LEVEL` — `debug | info | warn | error` (дефолт `info`)
- `GUARDRAIL_TICK_SECONDS` — интервал проверки guardrail в секундах в режиме polling (по умолчанию 10)
- `GUARDRAIL_WORKER_ENABLED` — включение режима обработки на основе событий (event-driven worker mode) (по умолчанию true)
- `GUARDRAIL_WORKER_BATCH_SIZE` — количество заданий, захватываемых за один цикл воркера (по умолчанию 50)
- `GUARDRAIL_WORKER_POLL_MS` — интервал опроса очереди воркера в миллисекундах (по умолчанию 1000)
- `GUARDRAIL_FALLBACK_SCAN_SECONDS` — интервал сканирования fallback в секундах (по умолчанию 300)
- `GUARDRAIL_LEADER_LOCK_KEY` — ключ строки для блокировки лидера (leader lease), обеспечивающий единственного активного воркера
- `GUARDRAIL_LEADER_TTL_SECONDS` — время жизни (TTL) блокировки лидера в секундах (по умолчанию 15)

## Архитектура

Следуем DDD: DI, и чёткое разделение слоёв
- `internal/domain` — сущности и бизнес логика
- `internal/app` — конфиг, связывание компонентов, event-diven guardrail + fallback scan
- `internal/infrastructure/db/postgres` — PostgreSQL адаптер.
- `internal/transport/http` — HTTP обработчики/DTO.
- `migrations` — SQL миграции.


## Реализовано/Не реализовано

tldr: Платформа является MVP и далеко не является полноценной. Во-первых, я очень поздно приступила к заданию, потому что оно было
скрыто, и мне понадобилось время, чтобы отыскать знакомых, которые поделились условием.
Во-вторых, я постаралась все основные требования реализовать полноценно, и сосредоточиться на архитектуре.
Но, по понятным причинам, пользовательский интерфейс, внешние интеграции и асинхронная архитектура на основе брокера сообщений не были реализованы в данной итерации
Реализовано:
- Базовые ендпоинты (health/readiness)
- Feature flags: создание, список, получение, обновление значения по умолчанию
- Эксперименты: создание, чтение, редактирование черновика, процесс ревью, одобрение/отклонение/запрос изменений, запуск, пауза, возобновление, завершение
- Прием событий с дедупликацией по event_id 
- Обработка отложенных/пришедших не по порядку событий через pending queue
- Отчеты по эксперименту и вариантам 
- Guardrails со срабатывающей паузой
- Аудит для lifecycle, ревью, изменений конфига, пересчёта и действий guardrail
- Локально воспроизводимое окружение через Docker Compose + Makefile 
- Воркер guardrail внутри PostgreSQL с ретраями, захватом заданий из очереди и защитой лидера (leader lease protection)

Список API эндпоинтов доступен в openapi.yaml

Не реализовано:
- UI дашборды
- Интеграция аутентификации/авторизации с реальным провайдером
- Каналы уведомлений (email, Slack, webhook)
- Каталог экспериментов 
- разрешение конфликтов между пересекающимися экспериментами/доменами 
- Отдельный аналитический слой хранения для высокообъемной отчетности (в кликхаус условном)
- Конвейер обработки событий на основе брокера сообщений (Kafka, NATS и др.)
- Выделенный сервис воркера, отделенный от API-процесса 
- Развитый стек наблюдения (дашборды метрик/трассировки, алерты, SLO-слой)

Причины:
Данные реализации скорее подходят для следующей итерации разработки и не входят в ядро платформы.
Для некоторых из пунктов нужна усложненная инфраструктура.

## Надёжные паттерны

Что сделано по паттернам надёжности:
- идемпотентность
- аудит-лог
- версионирование экспериментов
- детерминированный хеш
- воспроизводимость
- защита от повторного срабатывания guardrail

1) **Идемпотентность** обеспечивается по уникальному event_id в БД (events.event_id).
Повторная доставка проверяется на совпадение с уже сохранённым payload:
    - тот же payload → учитывается как дубликат (duplicate);
    - другой payload при том же event_id -> отклонение как конфликт.
Эндпоинты создания поддерживают заголовок Idempotency-Key:
    - `POST /v1/flags`
    - `POST /v1/experiments`

2) **Аудит-лог**
Записи аудита пишутся для:
- создания флага / обновления значения по умолчанию
- переходов по жизненному циклу эксперимента
- действий ревью
- обновления конфига эксперимента (изменение версии)
- срабатываний guardrail
- выполнения replay

Эндпоинт чтения аудита:
- `GET /v1/admin/audit/{entityType}/{entityID}`

3) **Версионирование** 
- Явный путь обновления только в черновике:
    - `POST /v1/experiments/{id}/update`
- Каждое обновление увеличивает Experiment.Version.
- В Experiment.Versions добавляется неизменяемый снимок.
- Ветка decide подмешивает version во вход хеша и сохраняет config_version в решении.


4) **Детерминированное хеширование**
Корзина (bucket) решения детерминирована от:
- subject_id
- experiment_id
- version
- salt

5) **Воспроизводимость (replay)**:
Сырые события сохраняются (таблица events).
Совмещенные (с атрибутами) события хранятся отдельно (attributed_events)
- Эндпоинт replay:
    - `POST /v1/admin/replay`
- Поведение replay:
    1. удалить строки атрибуции для эксперимента и окна времени;
    2. пересобрать варианты совмещения (пусть будет атрибуция) из сырых событий и решений;
    3. записать запись в аудит.

6) **Защита от повторного guardrail**
- Отдельная таблица guardrail_triggers с уникальным incident_key.
- Ключ инцидента включает:
    - id эксперимента
    - метрику
    - действие
    - временной bucket
- Один и тот же инцидент нельзя вставить дважды; повторное срабатывание игнорируется.

## Design Trade-offs

### 1. Синхронный HTTP API вместо асинхронной обработки команд

Синхронная модель запрос/ответ для создания/обновления, decide и приёма событий.

Почему:
- проще тестировать локально;
- ниже риск реализации для MVP

При высокой нагрузке слабее развязка, чем у полностью асинхронного конвейера команд.

### 2. PostgreSQL как основное хранилище и очередь

PostgreSQL как источник правды и как очередь для event-driven обработки guardrail.

Почему:
- самая удобная реализация для MVP;
- одна технология хранения для флагов, экспериментов, событий, аудита, replay и задач воркера;
- проще локальный запуск и меньше операционной нагрузки

Не лучший долгосрочный выбор для очень высоконагруженных streaming-сценариев, поэтому на второй итерации нужно будет его менять

### 3. Без Kafka в текущей итерации

Остаться внутри PostgreSQL вместо подключения Kafka.

Почему:
- Kafka добавляет брокер, партиции, consumer groups, семантику доставки и большую операционку;
- для текущего объёма работ эта сложность не оправдана;
- очередь на Postgres достаточна, чтобы реализовать event-driven подход и надежность.

### 4. Модульный монолит вместо микросервисов

Один разворачиваемый процесс с явными внутренними границами.

Почему:
- проще сохранять согласованность бизнес-правил;
- быстрее внедрить;
- проще дебажить и поднимать.

Проблема: Меньше независимых вариантов масштабирования, чем у отдельных сервисов.

### 5. JSON-снимки версий эксперимента вместо отдельной таблицы версий

Только дополняемые снимки внутри `experiments.versions`.

Почему:
- достаточно, чтобы показать версионирование и воспроизводимость.

Проблема: очевидно слабее аналитическая гибкость, чем у нормализованной таблицы `experiment_versions`, нужно менять во второй итерации.
